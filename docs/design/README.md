## 🎯 快速理解

### 业务模式

```
产品类型:  GPU算力 | 存储 | LLM Token
计费模式:  预付费(包年包月) + 后付费(按量计费)
计费粒度:  秒级计量 → 小时出账
租户体系:  Tenant → Organization → Project → User
```

### 技术选型

```
应用层:    Go 1.25 + Gin/Echo
业务数据:  MySQL 8.0 (订单、账单、用户)
计量数据:  ClickHouse (海量时序数据)
缓存:      Redis 7.x (定价规则、汇率)
消息队列:  Kafka 3.x (事件驱动)
```

### 核心流程

#### 预付费流程 (包年包月)
```
用户下单 → 查询价格 → 生成订单 → 立即出账 → 用户支付 → 开通资源
```

#### 后付费流程 (按量计费)
```
开通资源 → 秒级计量 → 小时聚合 → 生成账单 → 自动扣费 → 余额不足告警
```

## 🏗️ 架构特点

### 双存储架构

| 存储 | 数据类型 | 数据量 | 保留策略 |
|------|---------|--------|---------|
| **MySQL** | 订单、账单、用户 | 万-百万级 | 永久 |
| **ClickHouse** | 秒级计量明细 | 亿-百亿级 | 6个月 |

### 双主键设计

```sql
CREATE TABLE tenants (
  id          BIGINT PRIMARY KEY,           -- 物理主键 (数据库内部)
  tenant_id   VARCHAR(64) UNIQUE NOT NULL,  -- 业务主键 (业务层使用)
  ...
);
```

**优势**:
- ✅ 业务ID可读性强 (`T20240117001` vs `id=1001`)
- ✅ 跨系统集成方便
- ✅ 便于沟通反馈

### SPU/SKU 产品模型

```
SPU: NVIDIA A100 GPU (产品族)
  ├─ SKU: A100 40GB 北京 25Gbps
  ├─ SKU: A100 40GB 北京 100Gbps
  ├─ SKU: A100 80GB 北京 25Gbps
  └─ SKU: A100 40GB 上海 25Gbps
```

## 🔍 核心设计决策

### 为什么使用 ClickHouse?

**问题**: MySQL 无法承载海量秒级计量数据
- GPU按秒计量: 1台GPU/天 = 86,400条记录
- 1000台GPU/月 = 25.9亿条记录

**方案**: ClickHouse 列式存储 + 压缩
- 写入性能: 单节点 10万 TPS
- 压缩比: ZSTD 压缩 10:1
- 查询性能: 百亿数据秒级响应

### 为什么要 SPU/SKU?

**问题**: 扁平产品设计难以管理多规格

**方案**: 电商成熟的 SPU/SKU 模型
- SPU统一管理产品族 (A100 GPU)
- SKU管理具体规格 (40GB 北京 25Gbps)
- 支持多维度定价 (规格/地域/时段)

### 为什么本位币是 CNY?

**原因**:
1. 主要客户在国内
2. 财务核算用人民币
3. 减少汇率转换频率
4. 降低汇率波动风险

## 📝 设计原则

### SOLID原则
- **S** (单一职责): 订单、计量、账单、支付各自独立
- **O** (开闭原则): 新产品通过配置接入,无需改代码
- **L** (里氏替换): 接口设计支持多种实现
- **I** (接口隔离): 服务间通过明确的API通信
- **D** (依赖倒置): 依赖抽象接口而非具体实现

### 其他原则
- **KISS**: 追求代码和设计的极致简洁
- **YAGNI**: 仅实现当前明确所需的功能
- **DRY**: 杜绝重复代码
